Central repository for **feature-level documentation** of the BillyApp ecosystem.  

Each **top-level folder** in this repo represents **one app feature** (e.g. `ble/`), and each feature folder contains all the **architecture** and **implementation** documents for that feature, versioned over time.

---

## 🧱 Concept & Conventions

### Directory Structure

At the root of the repo, directories are split between **system folders** (prefixed with `_`) and **feature folders**:

```text
.
├── .github/          # CI/CD workflows and scripts
├── _templates/       # Official Corporate LaTeX templates (Ignored by CI)
├── ble/              # "BLE feature" documentation
├── <next-feature>/   # future feature folders
├── LICENSE.txt
└── README.md

```

**Rules**

* **System Folders**: Folders starting with `_` (like `_templates`) contain meta-files and are explicitly ignored by the auto-indexing script.
* **Feature Folders**: One folder per feature (e.g. `ble`, `chat`, `backend_api`).
* Folder name is **lowercase**, **kebab_case** or **snake_case**.
* Everything strictly related to that feature’s docs lives under its feature folder.

---

### Document areas inside a feature

Inside each feature folder, we group documents by **area** (architecture, implementation, etc.).

Typical **area examples**:

* `architecture_` — high-level architecture, sequence diagrams, responsibilities.
* `implementation_` — low-level client implementation details, class diagrams, flows.

---

### Versioned document directories

Each **document area** contains one or more **version directories**, each named:

```text
v_<MAJOR>_<MINOR>_<PATCH>

```

Examples:

* `v_1_0_0`
* `v_1_1_0`
* `v_2_0_0`

Inside each version directory you’ll typically find:

* `.tex` source (single entry point per document)
* `.pdf` export (canonical rendered output for that version)

> ✅ **Always consider the highest semantic version as the “current” doc for that area.**
> Older versions remain for historical context and audits.

## 📄 Working with LaTeX & PDFs

This repo is designed to be friendly for LaTeX-based workflows.

### LaTeX toolchain

You can use any standard LaTeX distribution:

* **TeX Live** (Linux/macOS)
* **MacTeX** (macOS)
* **MiKTeX** (Windows)
* Editors: VS Code + LaTeX Workshop, Texmaker, TeXstudio, etc.

From a given version folder, compile the main `.tex` file:

```bash
cd ble/architecture_client_server/v_1_1_0

# using latexmk
latexmk -pdf architettura_ble_lato_client_e_server.tex

# or standard pdflatex
pdflatex architettura_ble_lato_client_e_server.tex

```

The resulting `*.pdf` stays committed alongside the source.

## 🤖 Automation & CI/CD

This repo includes **GitHub Actions** for a lightweight, corporate-style docs pipeline.

1. **Keeps the feature index in this README in sync** with the actual folder structure:
* The script `.github/scripts/update_readme.py` scans the repo for feature & version folders and regenerates the table under `📂 Feature Index`.

* After merging to `main`, CI runs the script and **commits any required README changes** back to the branch.

## 🔧 Local workflow (Adding new docs)

Do not format documents from scratch. Use the centralized LaTeX template to ensure all documents share the same structure, semantic boxes, and typography.

### 1. Create the folder structure

Strictly respect this hierarchy for any new feature or component:
`[feature_name]/[document_area]/v_[MAJOR]_[MINOR]_[PATCH]/`

```bash
mkdir -p user_management/architecture/v_1_0_0/

```

### 2. Copy the Official Template

Copy `report.tex` from the `_templates` utility folder into your new directory, renaming it appropriately:

```bash
cp _templates/report.tex user_management/architecture/v_1_0_0/architecture_user_management.tex

```

### 3. Fill the Metadata

Open the new `.tex` file and update **only** the variables in the frontmatter:

* `\title{\textbf{[Document Title]}}`
* `\author{\textbf{[Your Name / Squad]}}`
* `\date{Version 1.0.0 \\ \today}`

### 4. Compile the PDF

Ensure it compiles correctly before opening a Pull Request:

```bash
cd user_management/architecture/v_1_0_0/
pdflatex architecture_user_management.tex

```

### 5. Commit your changes

> ⚠️ **CRITICAL:** Commit only the `.tex` source file and the resulting `.pdf`. **NEVER** commit intermediate build artifacts (`.log`, `.aux`, `.toc`, `.synctex.gz`, etc.). They pollute the Git history. Our `.gitignore` is configured to drop them, do not force-add them.

```bash
git add user_management
git commit -m "docs(user_management): add architecture v_1_0_0"

```
